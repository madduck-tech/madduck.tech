A while ago, I got a **GMKtec EVO-X2**. I decided to use this small computer for experiments with AI at home: running language models, generating images, and finding out what I could adapt to my own tasks.

The idea was simple: have a machine where I could swap models, adjust settings, connect tools, and figure out how everything works. Load one model, have a conversation, try another, compare. Switch to images. Eventually discover that all of this could use a small control panel.

That is how the EVO-X2 gradually became a home AI lab. Complete with Kubernetes, an API, a custom dashboard, and a button to reboot into Windows. Games still exist.

## What kind of device is this?

The [EVO-X2](https://www.gmktec.com/products/amd-ryzen%E2%84%A2-ai-max-395-evo-x2-ai-mini-pc) is a mini PC built on AMD Strix Halo. Mine has a Ryzen AI Max+ 395, integrated Radeon 8060S graphics, **128 GB of LPDDR5X, and a 2 TB SSD**. The processor has [16 cores and 32 threads](https://www.amd.com/en/products/processors/laptop/ryzen.html).

It is a full computer: install an ordinary OS, work, play games, run containers. My primary OS is Ubuntu Server, with Windows 11 kept alongside it in a dual-boot setup.

Memory is particularly interesting for local models. The CPU and integrated graphics share physical memory, and the GPU can access a substantial portion of it. I have configured a 16 GB UMA frame buffer plus another 96 GB through GTT, the mechanism for GPU access to system memory. That gives the GPU access to **112 GB within the machine's total 128 GB**.

This leaves room to experiment with LLMs whose weights occupy tens of gigabytes, reserve space for context, and try keeping several models loaded. But 128 GB does not promise high speed on its own. The model still needs computation, and memory is shared with the OS and other services.

The runs described here use the Radeon through Vulkan or ROCm. This particular project has not reached the processor's separate NPU yet.

## How the experiments started

The repository preserves the journey: initial Ollama settings, the move to llama-server, experiments with engines and models, memory configuration, and generation optimizations. Eventually I wanted more precise control over each model, and **llama.cpp in server mode** became the foundation.

There are now nine configured models behind it: Qwen and Qwen Coder variants, Ornith, gpt-oss-120b, and the large Qwen3.8-Flash-Next. They provide options for conversations, code, reasoning, and requests with images.

A large number in the name does not always mean a proportionally slow model. A mixture-of-experts model activates only some of its experts at each step. A model with tens of billions of parameters can therefore generate at a useful pace, while still needing plenty of memory to store its weights.

There are two ways to use the setup. **Open WebUI** handles conversations: open a browser, choose a model, ask a question. **LiteLLM** provides a shared API gateway for my programs, with short model names and access keys. Clients use one endpoint and select the model in the request.

Open WebUI is configured for document work, with local embeddings for retrieval. Web search connects to SearXNG on another home server. Generation runs on the EVO-X2; enabling internet search naturally sends the relevant searches outside the home network.

There is also a SillyTavern configuration for experiments with characters and role-playing conversations. A shared backend lets me try different interfaces without maintaining a separate set of models for each one.

## Why Kubernetes ended up at home

The EVO-X2 runs **MicroK8s**. The LLM server, API gateway, web chat, and image generation run in containers, with their configuration kept as manifests in the repository.

You certainly do not need this whole setup to try your first local model. But this lab already has multiple services, each with its own dependencies, data, and startup requirements. Kubernetes gives me a common way to describe, restart, update, and inspect them.

Model weights and user data live on persistent volumes. Recreating a container should not erase conversations or trigger another download of tens of gigabytes. An ingress exposes separate addresses for chat, the API, images, and management.

GPU management is particularly useful here. There is one physical GPU. I configured each GPU service to request it through the AMD device plugin. If llama-server owns the device, GPU ComfyUI waits for it to become available.

This is the resource-sharing policy I chose for the lab. It prevents two heavy workloads from unexpectedly competing for memory and interfering with each other.

## A custom dashboard instead of a collection of commands

Remembering which container is running and what to stop before generating an image gets old fairly quickly. So the EVO-X2 got its own dashboard.

It displays CPU load and temperature, RAM usage, GPU memory and GTT, graphics temperature, and disk usage. Below that are services, their status, and links to their interfaces. Alongside them sit the active profile, the current GPU owner, and action history.

There are three main profiles:

- **LLM** — llama-server, LiteLLM, Open WebUI, and a separate CPU ComfyUI instance.
- **Images** — GPU ComfyUI and the SwarmUI interface, plus supporting CPU services.
- **Immich** — the GPU goes to the service processing the home photo library.

Switching a profile starts a sequence: stop the previous GPU service, wait for the device to be released, and start the new one. The interface shows the current phase. This takes time: one acceptance test measured about 157 seconds to switch to images and 86 seconds to return to LLMs. That is one particular run, but it explains why the switch needs a progress indicator.

The dashboard itself lives on another home mini-server. Its FastAPI backend runs on the EVO-X2 under systemd. That separation is especially useful when the EVO is off: the management page remains available and can send **Wake-on-LAN**.

It can also shut the machine down, reboot Linux, or reboot into Windows. A fairly ordinary use case emerges: finish an experiment with models, switch to games.

Startup had its own quirks. Sometimes the GPU plugin and services came up in an unfortunate order. A boot guard now remembers the profile during a clean shutdown, waits for the GPU to be ready at the next boot, and restores the appropriate services.

## Is 30 tokens per second any good?

With suitable models, **around 30 tokens per second is a realistic reference point** on this machine. That includes models with tens of billions of parameters, including MoE models, rather than only the smallest options.

Here are several results from the shared-server checks on September 27:

| Model | Generation,<br>tok/s |
|---|---:|
| Qwen3.6-35B | 33.3 |
| Qwen3-Coder-Next-80B | 33.4 |
| Ornith-1.5-35B | 38.6 |
| gpt-oss-120b | 26.5 |
| Qwen3.8-Flash-Next | 28.6 |
{: .evo-results }

These are individual generation measurements after processing long inputs, each with 512 output tokens including internal reasoning. Input lengths differed: about 130,000 for gpt-oss, 199,000 for Qwen3.6, Coder-Next, and Ornith, and 204,000 for Flash-Next. The table shows speeds achieved, not a ranking under identical conditions.

To understand the waiting time, divide the output length by the speed. **At a steady 30 tokens per second**, that gives:

| Generated output | Time |
|---|---:|
| 300 tokens | 10 seconds |
| 500 tokens | About 17 seconds |
| 1,000 tokens | About 33 seconds |
| 2,000 tokens | About 67 seconds |
{: .evo-results }

This calculation covers generation alone. A token is a piece of text, not necessarily a whole word; the relationship depends on the language, model, and whether it is producing prose or code. Thinking models also spend some generated tokens on internal reasoning.

**My assessment: this is a practical speed for personal chat.** You can read a short response as it appears. A detailed explanation takes tens of seconds. The pace also looks reasonable for background document processing when the volume of requests is modest.

For an agent making dozens of sequential calls, waiting times add up. Twenty generations of a thousand tokens each at this speed already total about eleven minutes, before input processing and tool execution. A conversation and a long autonomous task therefore have different speed requirements.

Not every model maintains 30 tokens per second. Dense Qwen3.8-27B produced roughly 19–22 on short inputs in my tests and slowed significantly on very long ones. There is also the time spent processing the request before answering. In the Flash-Next experiment, a fresh 200,000-token input took roughly 14.5 minutes before the first output token. That is a separate heavy workload, rather than a reference point for a normal short conversation.

## Image generation: ComfyUI and SwarmUI

Images are the other major part of this experiment. **[ComfyUI](https://github.com/Comfy-Org/ComfyUI)** is the foundation: a graph where I can assemble model loading, a text prompt, generation settings, and result processing. It runs through ROCm on the EVO-X2, in a custom container for AMD.

When I just want to choose a model and write a prompt, **[SwarmUI](https://github.com/mcmonkeyprojects/SwarmUI)** provides a more familiar interface to the same ComfyUI backend. SwarmUI itself does not occupy the GPU; computation stays with ComfyUI.

The repository contains workflows for **FLUX.1 dev, FLUX.1 schnell, and SDXL**. For example, there is a 1024 × 1024 FLUX dev workflow with 25 steps, and a small 512 × 512, four-step workflow for schnell. More involved experiments include cyberpunk scenes, face processing with ReActor, and an image-to-video workflow using Wan 2.2.

Video is already a different scale of task: the saved Wan workflow specifies 81 frames at 480 × 704 and 30 steps. Having the workflow does not establish how fast or how well it runs. The materials do not yet contain a verified image/video timing series comparable to the LLM tests, so I will not invent a seconds-per-image figure here.

For images, I select the Images profile and the GPU moves from language models to ComfyUI. There is also a separate CPU ComfyUI instance connected to the web chat. It can run alongside the LLM, but is substantially slower than the GPU version.

## What needed extra work

The AMD software stack contributed some entertainment of its own. LLMs ended up using Vulkan, while ComfyUI uses ROCm. ComfyUI's compatible PyTorch and dependency versions are pinned. Otherwise, installing another custom node can pull in a CUDA build over a working ROCm setup.

Then it turned out that even 128 GB needed careful allocation. A simple “keep no more than three models loaded” rule is insufficient: three models can have very different memory requirements.

That led to a dispatcher in front of llama-server. It uses measured memory budgets, loads a model when space is available, and unloads idle models when another needs the resources. An active request keeps its model until completion. Flash-Next, for example, runs alone in the tested switching scenario.

There was also a less obvious issue: some memory remained in the GPU driver's pool after a model unloaded. A separate check recovered 21.3 GiB in five seconds by releasing unused pages. Without memory monitoring, that would simply look like “the old model has stopped, so why won't the next one fit?”

Eventually, the disk accumulated too many weights as well. Usage reached 85%, and Kubernetes began removing unused container images. I had to reconsider the model collection and free roughly 229 GB. Two terabytes sounds generous until you start keeping several quantizations of the same model.

## What else the machine does

The EVO-X2 also helps with **Immich**, my home photo library. Its main server runs elsewhere, while ML work is offloaded here: face recognition and search by image content. When the Immich profile is inactive, the setup falls back to CPU processing on the main server.

There is also a prepared Unsloth Studio profile for fine-tuning experiments. That remains a starting point: a deployment manifest does not establish that successful fine-tuning on AMD has already happened.

I like being able to develop this gradually. Today, a conversation with a local model; tomorrow, images; later, integrations with my programs or home automation. The [AI greenhouse idea]({{ '/en/blog/ai-dacha/' | relative_url }}), for instance, now has an obvious place to run and test models.

For me, the EVO-X2 is a working environment for these experiments. Suitable LLMs generate at a useful pace, images have their own environment, and services can be managed from a browser. Next, I want to test concrete value: how well models handle my tasks and what deserves to stay running.

I wanted to experiment with neural networks. Along the way, I acquired another home server that needs attention. Everything is proceeding as expected.
