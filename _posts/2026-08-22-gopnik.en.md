The agent may not be lying. By its own check, everything really does add up. It is just that the agent wrote the code, the agent thought up the tests, and the agent is the one who said the final "done."

## It is far too easy for an agent to believe itself

There is a language model inside the agent. Underneath, it continues the text one token at a time. The instructions, the work so far, and the command output make up the context for each new step. That is how an agent can write code, run tests, and decide the job is done. But a coherent sequence of actions is no guarantee of a correct result.

Research has found language models agreeing with users even when the users are wrong, a behavior known as *sycophancy*. One possible cause is fine-tuning on human ratings: if answers that support a user's position receive higher ratings, the model can learn to reproduce that behavior.<sup>[1](#source-1)</sup>

We developers add a habit of our own. I have more than once written tests to confirm what I already believed: feed in the expected data, get the expected answer, tick the box. Far less often does a test start with the question, "What should break this?"

When an agent does the same, one mistake travels through the whole job. First it lands in the code. Then in the test, because the test is built on the same assumption. The tests pass, the agent takes that as confirmation and writes "Done." What actually happened is that it agreed with itself three times.

Telling an agent to check itself again sometimes helps, sometimes changes nothing, and sometimes degrades an answer that was right. Research on intrinsic self-correction in reasoning has found the same limitation: without an external signal, a second look by the same author is not independent evidence.<sup>[2](#source-2)</sup>

## A test should hunt for a bug, not for confirmation

Edsger Dijkstra explained in 1969 what tests cannot prove:

> Program testing can be used to show the presence of bugs, but never to show their absence.
>
> <cite>Edsger Dijkstra, [Notes on Structured Programming, EWD249](https://www.cs.utexas.edu/~EWD/transcriptions/EWD02xx/EWD249/EWD249.html)</cite>

A red result gives you a specific failure: here is the input, here is the actual behavior, here is what was required. A green result tells you only about the conditions you picked. On this input and in this build, the check found no failure. It says nothing about any other input.

Ten years later, Glenford Myers turned that asymmetry into a working rule. Testing is running a program with the intent of finding errors, and a good test is one with a high probability of finding an as-yet-undiscovered defect.<sup>[3](#source-3)</sup>

<aside class="article-callout" aria-label="The idea in Gopnik's street voice">
  <p class="article-callout-label">Translated from academic into Gopnik's early-2000s Mytishchi voice</p>
  <p>A test should call the code's bluff. Not a pat on the head. Snap the thing over your knee and show everyone where it cracked.</p>
</aside>

What changes from here is not one check but the way the work runs. Written code does not go straight to "done." First someone makes an honest attempt to break it in a way that can be repeated. If that works, the author gets a counterexample instead of a reviewer's opinion.

The principle matters especially in agent-driven development. The same agent writes the implementation, picks the checks, reads their output, and draws the conclusion. A mistake in the original assumption can survive all four steps. So checking has to move into a role of its own, where the agent stops defending what it built and starts looking for grounds not to call the change ready.

## How Gopnik works

That role belongs to Gopnik, a set of three skills.

<div class="skill-grid" role="group" aria-label="The three Gopnik skills">
  <section class="skill-card">
    <span class="skill-card-label">onboarding</span>
    <h3>gopnik-setup</h3>
    <p>Gets Gopnik oriented in the project: finds and runs the project's own checks, works out where the finished result gets used, and records reproducible routes for the runs that follow.</p>
  </section>
  <section class="skill-card">
    <span class="skill-card-label">claims</span>
    <h3>gopnik-critic</h3>
    <p>Tries to refute a claim before it is published: checks it against primary sources, then puts it through an independent check whose task is to prove the opposite.</p>
  </section>
  <section class="skill-card">
    <span class="skill-card-label">readiness</span>
    <h3>gopnik</h3>
    <p>Looks for what can break, attacks the code and the delivered result, then returns a verdict with its evidence and the limits of what was checked.</p>
  </section>
</div>

`gopnik-setup` runs when you first add it to a project and is not repeated for every task. After that, the skills can be used separately. In our working cycle, the roles break down like this:

<div class="workflow" aria-label="An example working cycle with Gopnik">
  <p class="workflow-title">One of our working cycles</p>
  <ol>
    <li>Issue from the tracker<span class="workflow-owner">the team</span></li>
    <li>Critique of the framing and the approach<span class="workflow-owner">gopnik-critic</span></li>
    <li>Implementation<span class="workflow-owner">the main agent</span></li>
    <li>Attempt to break the change<span class="workflow-owner">gopnik</span></li>
    <li>Verdict and evidence<span class="workflow-owner">gopnik</span></li>
  </ol>
</div>

The last step is the verdict. Gopnik does not stop at a list of the commands it ran: it answers whether the change is ready and attaches the evidence.

```text
NOT READY
Broken: re-running the install leaves a stale file behind.
Revision: 6eafa7d - the re-check produced the same result.
Abridged: the command, file path, and full output are omitted here.
```

A counterexample means `NOT READY`. `READY` appears when the mandatory checks pass, there are no blockers, and the last round of checking covers the exact revision. Gopnik names separately the limits of what it did not check.

## What it looked like in practice

On a large internal project where agents were heavily involved in development, one of the first runs with Gopnik turned up four classes of defect. We fixed the bugs and pinned the cases down with tests.

## What "done" means now

Gopnik does not prove there are no bugs left in the code. What it changes is who gets to say "done." One green run is no longer enough: the agent has to show how it tried to break the change, which version it checked, and what it did not check.

Next time an agent tells you everything works, do not ask it to check again. Ask how it tried to call its own bluff.
